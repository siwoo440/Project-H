# Part 1. 전투 움직임 — `BattleUnitMotion`

## 가장 중요한 규칙 : 그림만 움직인다

전투 유닛의 **실제 위치**는 사거리와 이동 계산에 쓰인다. 연출하려고 위치를 흔들면 "공격이 닿는가"가 달라져 **전투 결과가 바뀐다.**

그래서 유닛 안의 **바디 그림만** 움직이고 유닛 자체는 건드리지 않는다.

## 네 가지 움직임

| 움직임 | 언제 | 내용 | 시간 |
| --- | --- | --- | --- |
| 대기 | 늘 | 위아래로 4픽셀 오르내림 | 한 번에 약 2.9초 |
| 공격 | 공격 · 스킬 · 궁극기 순간 | 적 쪽으로 26픽셀 튀어나갔다 복귀 | 0.07초 나가고 0.16초 돌아옴 |
| 피격 | 맞는 순간 | 뒤로 14픽셀 밀렸다 복귀 | 0.04초 밀리고 0.14초 돌아옴 |
| 쓰러짐 | 체력 0 | 뒤로 22도 기울며 10픽셀 내려앉음 | 0.30초 |

- 나갈 때는 곧게, 돌아올 때는 부드럽게 감속한다. 같은 속도로 오가면 기계처럼 보인다
- **유닛마다 박자가 다르다.** 유닛 이름으로 시작 위치를 정했다. 모두 똑같이 오르내리면 군무처럼 보인다
- 쓰러짐은 0.30초다. 쓰러진 유닛이 전장에서 사라지기까지가 0.35초라서 그 안에 끝나야 한다
- 쓰러진 뒤에는 공격 · 피격 신호를 받지 않는다
- 부활하면 자세가 처음으로 돌아간다

## 연결한 곳

새 호출을 여기저기 넣지 않고, **이미 있던 세 지점**에 붙였다.

| 움직임 | 붙인 곳 | 이유 |
| --- | --- | --- |
| 공격 | `BattleActor.ShowAction` | 기본 공격 · 스킬 · 궁극기 · 보스 패턴이 모두 이 함수를 부른다 |
| 피격 | `BattleActor.FlashHitPreview` | 피해 · 보호막 피격이 모두 이 함수를 부른다 |
| 쓰러짐 | 뷰의 `ShowDefeatedPreview` | 아군 · 적군 사망 처리가 여기로 모인다 |

## 설정 연동

설정의 **"흔들림 줄이기"** 를 켜면 대기 · 공격 · 피격 움직임이 35%로 줄어든다. 멀미가 있는 사람을 위한 설정이라 화면 흔들림과 같은 취급을 했다.

## 겹침 순서

SD 그림은 색 상자보다 커서 위아래 유닛이 서로 겹친다. 세로 위치로 순서를 정해 **화면 아래쪽(가까운 쪽) 유닛이 앞에** 그려지게 했다.

| 층 | 순서 값 |
| --- | --- |
| 전투 배경 | -20 |
| **유닛** | **1 ~ 18** (세로 위치에 따라) |
| 전투 HUD | 20 |

유닛 순서가 배경 아래로 내려가거나 HUD 위로 올라가면 화면이 깨지므로 범위를 묶었다.

# Part 2. 컷인 전용 그림 자리

궁극기 컷인은 화면을 비스듬히 가로지르는 **높이 250의 좁은 띠**다. 77일차에 스탠딩을 얼굴 기준으로 확대해 넣었는데, 전용 그림이 오면 쓸 배치는 없었다.

| 그림 | 배치 |
| --- | --- |
| 전용 그림이 없음 | 스탠딩을 얼굴 기준으로 확대 (77일차) |
| **전용 그림 있음** | 너비 1500으로 놓고 **세로 가운데 띠만** 보여 줌 |

띠가 좁고 길어서 세로형 그림은 맞지 않는다. 가로 3:2 그림에서 **가운데 1/4**만 띠에 보이므로, 눈과 얼굴을 그 안에 그려 달라고 요청문에 적었다. 코드를 먼저 정해 두어 요청문의 규격과 실제 배치가 어긋나지 않는다.

발 위치가 같아서 유닛들이 같은 바닥에 선 것처럼 보인다. 78일차에 그림의 기준점을 발 쪽으로 잡아 둔 것과 맞물린다.

## 가져오기 크기 512

SD 그림은 화면 높이의 11%(보스 17%)로 작게 보인다. 4K 화면에서도 보스가 370픽셀을 넘지 않는다.

→ 게임이 읽어 들이는 크기를 **512**로 줄였다. 원본 PNG는 1024 그대로 두었으므로, 흐리면 `.meta`의 숫자만 바꾸면 된다.

# Part 5. 테스트 실패와 수정

Unity Test Runner에서 한 건이 실패했다.

```
Pulse_RisesToOneAndReturnsToZero
  Expected: True
  But was:  False
```

## 원인

"움직임이 끝나는 시각에 정확히 도달하면 끝난 것으로 본다"를 검사한 줄이었다. 끝나는 시각(0.07 + 0.16초)을 테스트에서 한 번, 함수 안에서 한 번 따로 계산했다.

Unity는 소수 계산을 중간에 **더 높은 정밀도로** 처리한다. 그래서 같은 식인데도 한쪽은 float로 반올림된 값, 다른 쪽은 반올림되지 않은 값이 되어 **경계에서 어긋났다.**

로컬 `dotnet build`로는 드러나지 않고 Unity에서만 나오는 종류의 문제다.

## 수정

- 함수 : 끝나는 시각을 float 변수에 담아 정밀도를 맞춘 뒤 비교
- 테스트 : 정확한 경계값 대신 끝나기 직전(-0.001초)과 직후(+0.001초)를 검사

게임 동작에는 영향이 없었다. 실제 전투에서는 시간이 조금씩 쌓이므로 경계에 걸려도 다음 프레임에 끝난다.

## 알아둘 점

- **전투 연출은 바디 그림만 움직일 것.** 유닛의 실제 위치는 사거리와 이동 계산에 쓰인다
- **소수의 경계값을 정확히 비교하는 테스트를 쓰지 말 것.** 직전 · 직후로 검사하고, 값 비교는 `Within`을 쓴다. Unity에서만 실패한다
- 움직임의 폭과 빠르기는 `BattleUnitMotionMath`의 숫자로 조절한다
- 궁극기 컷인 전용 그림은 **가로 3:2**이고 세로 가운데 1/4만 보인다
- SD 그림이 흐리면 `Resources/BattleUnits/*.png.meta`의 `maxTextureSize`를 1024로 올린다
- 그림 묶음을 받을 때마다 저장소가 커진다 (오늘 SD 60MB · 배경 15MB)
