
## 1. 보스 패턴 데이터 (신규)

로드맵상 보스는 계속 늘어난다. 지역 보스들, 그리고 Day83~84의 네메시스까지. 그래서 보스 행동을 **코드가 아니라 데이터로** 정의했다.

`BossPatternData`(`ScriptableObject`)는 세 부분으로 구성된다.

| 구성 | 내용 |
| --- | --- |
| `BossPhaseDefinition[]` | 진입 체력 비율 · 시간 강제 진입 초 · 공격력/공격속도 보정 · 표시 이름 |
| `BossPatternDefinition[]` | 종류 · 피해 종류 · 공격력 계수 · 부가 효과 · **예고 시간** · 쿨다운 · 해금 페이즈 · **저지 가능 여부** |
| 공통 설정 | 첫 패턴 대기 5초 · 패턴 간격 4초 · 전환 무적 1.5초 |

패턴 종류는 네 가지다.

```csharp
public enum BossPatternKind
{
    AreaStrike,        // 아군 전체 공격
    FocusStrike,       // 단일 대상 강타 + 기절
    SelfFortify,       // 보스 방어력 강화
    DisarrayRecover    // 보스 흐트러짐 게이지 회복
}
```

`MonsterData`에 `BossPatternData` 참조 필드 하나를 추가했다. **비어 있으면 기존처럼 일반 적으로 동작**한다. 데이터가 없는 몬스터는 이번 변경의 영향을 전혀 받지 않는다.

Day46에서 `ProjectHDataCatalog`가 폴더 스캔이 아니라 명시적 GUID 목록이라 보스 몬스터를 따로 등록해야 했던 적이 있다. 이번엔 패턴 데이터를 `MonsterData`가 **직접 참조**하게 해서 카탈로그 등록이 필요 없도록 설계했다.

## 2. 페이즈 판정 (신규, 순수 로직)

`BossPhaseResolver`는 MonoBehaviour가 아닌 static 클래스다. 입력(체력 비율·경과 시간·현재 페이즈)만 받아 결과를 돌려주므로 테스트가 쉽다.

규칙은 세 가지다.

1. **체력 조건 또는 시간 조건** 중 하나라도 만족하면 그 페이즈에 진입
2. 여러 단계를 한 번에 넘으면 **가장 높은 페이즈로 직행** (60%→10%로 한 방에 깎이면 2페이즈를 건너뛰고 3페이즈)
3. **한번 올라간 페이즈는 내려가지 않음**

```csharp
return Mathf.Max(clampedCurrent, reached);   // 회복해도 역행하지 않음
```

3번이 없으면 보스가 자기 회복을 하거나 체력 판정이 흔들릴 때 페이즈가 오르락내리락하며 연출이 반복되는 문제가 생긴다.

로드맵에는 "HP·시간·흐트러짐 기반 전환"이라고 되어 있었는데, 흐트러짐은 **페이즈 전환 조건이 아니라 패턴 취소 수단**으로 연결했다. 흐트러질 때마다 페이즈가 넘어가면 플레이어가 잘할수록 보스가 빨리 강해지는 역효과가 나기 때문이다.

시간 조건은 3페이즈에 180초로 걸어 두었다. 화력이 부족한 파티가 보스를 무한히 붙잡고 있는 상황을 막는 일종의 **광폭화 타이머**다.

## 3. 패턴 스케줄러 (신규, 순수 로직)

`BossPatternScheduler`는 "지금 어떤 패턴을 쓸 차례인가"만 판단한다. 역시 MonoBehaviour에 의존하지 않고, 모든 메서드가 시각(`now`)을 인자로 받는다.

**선택 규칙**

- 현재 페이즈에서 해금됐고, 쿨다운이 끝났고, 패턴 간격을 지난 것 중 **순환 선택**
- **직전 패턴은 한 번 건너뜀** — 단, 그것이 유일한 후보라면 허용

**예고(windup) 관리**

```text
TryBeginNext  →  예고 시작
TickWindup    →  예고 진행 (완료 시 true)
CompleteActive → 발동 확정, 쿨다운 적용
CancelActive  →  저지로 취소, 쿨다운은 똑같이 적용
Postpone      →  다음 패턴 시작 지연 (페이즈 전환 등)
```

**취소해도 쿨다운을 소모**하게 한 것이 핵심 설계다. 흐트러짐으로 강타를 막으면 보스는 16초 동안 강타를 다시 쓸 수 없다. 저지에 성공한 플레이어에게 확실한 보상이 돌아간다.

## 4. 보스 컨트롤러 (신규)

`BattleBossController`는 `BossPatternData`를 가진 적에게만 붙는다. `BattleScreenController`의 적 생성 루프에서 부착한다.

**기본 공격은 기존 `BattleBasicAttackController`가 그대로 담당**하고, 보스 컨트롤러는 그 위에 패턴만 얹는다. 기존 전투 흐름을 전혀 건드리지 않는 구조다.

매 프레임 처리 순서는 다음과 같다.

```text
① 페이즈 판정 → 올라갔으면 전환 처리
② 전환 무적 중이면 중단
③ 예고 중이면 → 저지 / 정지 / 진행 / 발동 판정
④ 기절·흐트러짐 중이면 새 패턴 시작 안 함
⑤ 다음 패턴 예고 시작 시도
```

**예고 중 상황별 처리**

| 상황 | 결과 |
| --- | --- |
| 저지 가능 패턴 + **흐트러짐 발생** | 즉시 취소 + 금색 `저지!` |
| 일반 기절 (예: 이브 궁극기) | 예고 진행만 멈췄다가 재개 |
| 저지 불가 패턴 + 흐트러짐 | 취소 안 됨. 경직 동안 멈췄다가 재개 |

시간은 `Time.time`(배율 적용 시간)을 쓴다. Day50 리듬 챌린지로 전투가 일시정지되면 보스 패턴도 함께 멈춘다.

## 5. 페이즈 전환 처리

페이즈가 올라가는 순간 다섯 가지가 일어난다.

1. 진행 중이던 예고 정리
2. **공격력·공격 속도 보정** — 같은 출처 키로 덮어쓰기 때문에 2→3페이즈 전환 시 누적되지 않고 교체됨
3. **1.5초 무적** — 연출 중에 피해가 들어가 3페이즈를 순식간에 넘기는 것을 방지
4. 다음 패턴 지연 (무적 시간 + 패턴 간격)
5. 중앙 연출 `2페이즈 — 분노`

## 6. 무적·가속 Modifier 추가

페이즈 전환 무적과 공격 속도 증가를 표현할 수단이 없어서 `BattleRuntimeModifierKind`에 두 종류를 추가했다.

```csharp
AttackSpeedPercent = 10,   // 공격 속도 증가 (가속)
Invulnerable = 11          // 모든 피해 무시 (무적)
```

**무적**은 `BattleActor.ApplyDamage` 맨 앞에서 차단한다. 피격 번쩍임만 보여주고 피해는 0이다.

**가속**은 `BattleBasicAttackController`에서 공격속도에 곱한다. Day51의 둔화와 함께 계산되므로 둘이 동시에 걸리면 서로 상쇄된다.

두 종류 모두 Day51 상태이상 카탈로그에 등록했다. 보스 아래 칩에 청록 「무」, 파랑 「속」이 자동으로 뜬다. Day51에서 만들어 둔 안전장치 — **모든 Modifier 종류가 카탈로그에 매핑됐는지 검사하는 테스트** — 덕분에 등록을 빼먹을 수 없었다.

## 7. 패턴 효과 — 기존 도구 조합

새 효과 실행기를 만들지 않았다. 이미 있는 것들을 조합했다.

| 패턴 | 사용한 기존 기능 |
| --- | --- |
| 전체 공격 | `BattleDamageResolver.Resolve` |
| 집중 강타 + 기절 | 위 + `AddModifier(Stun)` + `RegisterRemovableDebuff` |
| 자기 강화 | `AddModifier(DefensePercent)` |
| 흐트러짐 회복 | `BattleDisarrayRuntimeState.RecoverDisarray` (신규 API 1개) |

피해가 `BattleDamageResolver`를 거치므로 **Day51 공격력 버프 · Day52 속성 상성 · Day53 흐트러짐 배율이 전부 자동 적용**된다. 보스는 어둠 속성이라 세레나(빛)에게 저항당하고, 무속성 캐릭터에게는 약점을 찌른다.

집중 강타 대상은 보스 Brain의 현재 타겟을 우선하고, 없으면 첫 생존 아군을 고른다. 기절은 정화 대상으로 등록해 세레나 궁극기로 풀 수 있다.

흐트러짐 회복 API는 **흐트러진 동안에는 동작하지 않는다.** 이미 무너진 보스가 게이지를 되돌려 경직을 끝내버리는 상황을 막기 위해서다.

## 10. 추가 작업 — 숫자키 번호 배지

HUD 초상화 좌상단에 **숫자키 번호(1~4)** 를 표시했다.

`BattleHudCardView.SetSlotNumber(int)`가 초상화의 자식으로 24×24 남색 배지를 만들고, `BattleScreenController`가 HUD 카드를 연결할 때 `SetSlotNumber(index + 1)`을 호출한다.

번호가 실제 숫자키와 일치하는지 확인했다. `BattleManualMoveController`의 숫자키 1~4는 아군 등록 순서로 슬롯을 채우는데, 그 등록이 HUD 카드 인덱스와 **같은 루프**(`SpawnAllies`)에서 일어난다. 따라서 배지 번호가 곧 누르는 숫자키다.

배지와 숫자 모두 `raycastTarget = false`다. Day48에서 초상화 궁극기 버튼이 raycast 설정 때문에 동작하지 않았던 경험이 있어서, 배지가 초상화 클릭을 가로채지 않도록 처음부터 막았다.

`BattleBossPatternTests` 신규 **14개**를 작성했다.

- 체력 비율별 페이즈 판정 (60%·25% 경계값, 한 방에 3페이즈 직행)

- 첫 패턴 대기 시간
- 페이즈별 패턴 해금 (1페이즈에서는 1페이즈 패턴만)
- 쿨다운 중 패턴 제외, 유일 후보는 연속 허용
- 직전 패턴 연속 사용 방지
- 예고 진행률 및 완료
- **취소해도 쿨다운이 적용되는지** (저지 보상)
- 패턴 간격과 지연
- 저지 불가 속성 보존
- 흐트러짐 회복 API — 절반 회복, 흐트러진 동안 회복 불가
- 무적·가속 Modifier 조회

**부동소수점 함정을 하나 피했다.** 지연 테스트에서 처음엔 `Postpone(3.9f, 5f)` 후 `8.9f`에서 시작 가능한지 검사했는데, 계산해 보니 `3.9f + 5f`의 정확한 값이 float로 표현 가능한 두 값의 **정중앙**에 떨어졌다. 반올림 방향에 따라 `8.9f`보다 크게도, 같게도 될 수 있어 테스트가 환경에 따라 흔들릴 수 있었다. Day49의 판정 경계 버그와 같은 종류의 문제라, 검증 값을 `4f + 5f = 9f`처럼 정확히 표현되는 값으로 바꿨다.

## 12. 작업 중 이슈

**csproj 중복 등록** — 로컬 빌드 검증을 위해 `.csproj`에 새 파일을 추가했더니 경고 CS2002(소스 파일 중복 지정)가 5개 났다. 작업 도중 Unity가 열려 있어서 이미 csproj를 재생성해 새 파일을 넣어둔 상태였다. 중복 항목을 제거해 경고 0으로 정리했다. `.csproj`는 gitignore 대상이라 커밋에는 영향이 없다.

**GUID 일치 확인** — 같은 이유로 Unity가 스크립트 `.meta`를 먼저 만들었다가 내가 생성한 `.meta`로 덮였을 가능성이 있었다. 에셋이 스크립트를 GUID로 참조하므로, `BossPatternData.cs.meta` ↔ `BossPattern_Leticia.asset`의 `m_Script`, `BossPattern_Leticia.asset.meta` ↔ `MON_BOSS_LETICIA.asset`의 `bossPattern` 참조가 모두 일치하는 것을 확인했다.
